## 使用

1. Mac 运行新版 Companion 和 Whisper Anywhere。沿用设备配对，在手机首页打开 24R。
2. 在 24R 设置中选整理模型。Ollama 填 Mac 可访问的地址和已安装模型；云端支持 OpenAI 兼容 Chat Completions；Quenda 填专属 Agent ID，以及可选 Workspace / Provider / Model ID。
3. 点「保存并测试连接」。API Key 只保存在 Mac 钥匙串，手机不会读回密钥。未配置模型时可以继续录音转写，文字保留，整理显示待重试。
4. 手机点「开始记录」。手机本机检测人声，无人说话不上传；检测到说话后，约 3 秒无语音提前发送，持续说话每满 60 秒发送一段，暂停时发送尾段。每段转写后文字先落盘到 Mac，再回复手机并保存；按日期与版本补同步。在今天页点「查看已识别文本」查看完整原文；首页时间线展示小时摘要。历史页可查看已有日期，日报中的待办可以勾选，完成状态也同步。
5. 默认按小时整理，21:30 生成日报，可改时间或手动生成。任务在 Mac 执行，需要 Companion 运行且电脑唤醒；恢复后补做遗漏的整理。手动在日报时间前生成，不会取消晚间更新。

## 留存与中断

- 默认没有音频文件：手机 PCM 在有限内存队列中传输，Mac 转发给独立 Whisper Anywhere；官方 C++ worker 改为标准输入中的 base64 Float32，不再写临时 PCM/WAV。
- 24R 拒绝尚未声明 `ephemeralAudio` 的旧识别服务。必须重启新版 Whisper Anywhere，才能开启 24R 转写。
- 「保留音频」和显式关键词功能才创建 WAV，最多 1/5/15 分钟。关键词在 Mac 返回转写后判断，因此受分段等待和识别耗时影响；需要立即保留时使用手动按钮。按采集时间过滤触发前数据；暂停、系统中断、到时会关闭文件。没有回溯。
- WAV 仅在 iPhone Application Support/Companion/24R/Clips，排除系统备份，可播放、导出、删除。文字服务和报告协议不上传片段。
- 全应用底部显示记录/保留状态，可以停止保留或暂停。App 重启不会自行恢复麦克风。
- Mac 断开时丢弃未主动保留的声音，不承诺离线补传；已完成文字保存在 Mac，重新连接后补回手机。中断时已有的临时转写标记为未校正，不自动进入总结。
- 24R 使用自动语言模式处理中英文，精度跟随 Whisper Anywhere 当前模型选择。24R 识别为低优先级。Whisper Anywhere 的交互式输入可以抢占；24R 不将旧结果插入光标，稍后自动尝试恢复。

## 整理与历史

- 每小时记录按来源 ID 去重；日报先归纳小时记录，再生成今日总结、待办、对策、历史关联、待确认。空模型结果不会标记为成功。
- 手动和定时模型调用不阻塞手机音频请求队列；失败保留原文，定时任务五分钟后重试。
- Ollama 请求使用 `/api/chat`、`stream:false` 和 `keep_alive`，列表检查用 `/api/tags`。文档：[chat](https://docs.ollama.com/api/chat)、[models](https://docs.ollama.com/api/tags)。
- 历史关联默认关闭，开启后检索指定天数内的相关 24R 日报。Quenda 还读取指定 Workspace 中近期最多 12 个会话、每个最近 30 条用户/助手文字，按文字匹配选择最多 6 条；不是全量语义搜索。
- Quenda 为每次整理建立独立会话，Provider/Model 覆盖只作用于该会话，不改 Agent 的全局配置。应使用只读工具的专属 Agent。需要人工确认/交互时停止等待，并显示会话 ID。
- 输入提示要求区分事实和建议，引用实际提供的来源。模型生成的关联仍需用户审阅。

## 实现边界

- iPhone 开启后台音频模式，24R 运行期间不主动暂停 Companion 连接；系统中断、锁屏、后台续航与网络切换仍需实机长时间验证。Mac 睡眠期间不做自动整理。
- iPhone 使用随包提供的 Silero VAD v6.2.1 CoreML 模型，明确设为 CPU-only，前台、锁屏及恢复后均采用相同路径，不下载模型、不上传给检测服务。16 kHz PCM，每 32 毫秒分析；人声概率达到 0.5 开始候选，持续至少 256 毫秒且不低于 0.35 才确认。两个阈值用于避免在边界反复切换，原有 2 秒内存上下文保留开始确认前的声音。可选系统分类/WebRTC 路径供回归使用，手机不静默降级回噪声误判较多的旧检测器。实际房间噪声、极低信噪比和长期耗电仍需实测。
- 160 毫秒只用于手机内部采集帧，不再逐帧发往 Mac。每段以单个请求发送，上一段转写时继续采集；最多一段传输中、一段待发送和当前采集段，处理跟不上会明确暂停，避免无界积压。Mac 在本机将整段分块送入独立 Whisper Anywhere。
- 手机采用今天 / 日报 / 历史 / 设置四个底部入口；Mac 使用左侧导航、中心内容、右侧状态栏。已识别文本每段完成后更新，不能在尚未上传时显示逐字识别。
- 当前仅云端 OpenAI 兼容协议；没有实现供应商特有协议、系统后台唤醒定时任务或音频云备份。
- 多台 Mac 的文本库合并、删除双端文字、报告编辑与语义检索不在此版本。

## 0.4.2 锁屏分析故障修复

用户反馈锁屏后出现 `Error during analysis` 并停止记录。用 SoundAnalysis 的错误回调注入该错误，复现其传播到手机采集循环的等待调用，导致循环退出、麦克风关闭。此前仅在 Mac 验证分类器，未覆盖设备锁屏的资源限制。

候选原因：声音分类资源受限、麦克风系统中断、后台主动断连。错误回调链已由回归测试确认；后台代码在记录期间保留连接，采集的后台音频配置也已开启。Apple 论坛有同类内置分类器锁屏 GPU 错误报告（[记录](https://developer.apple.com/forums/thread/757715)），这是替换该路径的依据，尚未从本机设备日志确认底层 GPU 错误码。

修复：手机从录音开始即使用纯 CPU 人声检测；可选 Apple 分类发生错误时回退到持续处理音频的 CPU 检测器，不抛出错误终止录音，也不把所有声音强制当作语音。分段、默认不保存音频和人工暂停行为不变。libfvad 的固定版本、许可证和专利声明位于 Vendor/Libfvad，发行包包含 ThirdPartyNotices.txt。

验证命令 `conda run -n kora swift test --filter DayRecordSegmentTests.testAnalysisFailureDoesNotStopCapture` 修复前捕获 `Error during analysis` 失败，修复后通过。新增真实语音样本 → CPU 检测 → 静音 → 片段发送链路验证；全量 58 项测试，56 通过、2 项可选测试跳过。Mac/iOS 构建及 iPhone 14 Pro 的 0.4.2（build 8）签名安装、启动成功。实机锁屏重现需用户操作，本轮安装后已请求复测；不能将上述测试视为实机锁屏通过或全天耗电验证。


## 0.4.3 视频播放与音频中断恢复

用户报告播放视频会中断采集，且视频结束后不会恢复。旧实现对任意 AVAudioSession 中断通知均结束音频流并注销监听，既未区分 began / ended，也没有恢复用户录音意图；会话还缺少 mixWithOthers。

24R 现在启用混音，尽量与视频/音乐播放共存。系统中断时保留记录意图，暂停硬件并按顺序输出尾部 PCM 与中断标记；页面显示等待恢复，已保留的 WAV 关闭。结束通知允许恢复时重新激活会话，并用当前音频格式重建 engine / tap / converter；短暂失败按 1、2、4、8、15 秒上限退避重试。没有恢复提示时等待回到前台；缺少结束通知也会在回到 App 时尝试恢复。音频服务重置和 engine 配置改变导致的停止同样触发重建。手动暂停取消所有重试与监听，之后的结束/前台事件不能重开麦克风。普通短时语音输入保持中断即取消的行为。

中断前尾段及时发送，恢复后重新检测与分段，不把系统占用期间的空缺拼进同一段。系统仍可能阻止其他应用同时使用麦克风，真实中断期间的声音无法补录。不能保证后台进程在所有系统状态下及时被唤醒；前台恢复是兜底。参考 Apple [中断处理](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions)、[mixWithOthers](https://developer.apple.com/documentation/avfaudio/avaudiosession/categoryoptions-swift.struct/mixwithothers)。

验证：把旧的中断即停止策略抽到 RecordingRecovery 后，`conda run -n kora swift test --filter RecordingRecoveryTests` 的中断→结束序列出现意图丢失和启动次数不足（1 而非 2），修复后 7 项全部通过。测试覆盖实际使用的恢复控制器和有界音频流，检查尾部数据完整、恢复后继续送入声音、手动暂停不恢复、重复通知、无结束通知、临时失败重试及取消。全量 65 项中 63 通过、2 项可选测试跳过；Mac/iOS 构建通过，0.4.3（build 9）已在 iPhone 14 Pro 上签名安装并启动；真实视频 App 抢占与系统通知交互仍需 iPhone 复测。


## 0.4.4 背景噪声触发上传

用户确认持续上传出现在风扇/空调等背景噪声环境，并反馈 0.4.3 在视频/微信期间不会退出记录；本次保留中断恢复机制。

定位：旧 WebRTC 模式 2 只需 160 毫秒中四分之一的 10 毫秒帧判为人声，即可开启整个上传片段。用确定性低通噪声模拟风扇、150/300 Hz 谐波模拟嗡声，真实检测器 → DayRecordSegmenter 链路在无讲话的两分钟样本中分别产生 2 次和 1 次上传。调到模式 3 仍会短暂误判；进一步提高投票门槛、增加起始确认虽然能挡住测试噪声，但损害低音量语音，因此未发布这些调参实验。

采用固定提交、随包分发的 Silero 模型，强制 `.cpuOnly`，不依赖后台 GPU。持续人声确认和分离的起止阈值避免短暂误判启动上传。UI 显示检测到说话/等待说话及本次成功上传段数；持续运行的麦克风用于本机检测，不代表持续网络上传。

`conda run -n kora swift test --filter SpeechNoiseTests` 验证三类无讲话背景信号不产生上传，以及原声和降低 20 dB 的语音叠加风扇噪声能上传、讲话结束后不被风扇拖成长段。两组语音约为 31 dB、11 dB 信噪比。另测降低约 30.5 dB、约 0.65 dB 信噪比的样本仍可能漏检；这个极低信噪比边界未被修复，未作为已支持场景。合成噪声用于固定回归，不能代替用户实际房间的录音测试。模型来源、固定版本、哈希及许可证见 Vendor/SileroVAD，包内 ThirdPartyNotices 包含许可。

0.4.4 验收：全量 67 项测试，65 通过、2 项可选测试跳过；Mac/iOS 构建通过，iPhone 14 Pro 签名安装并启动成功。安装产物中模型资源全部与固定 SHA256 清单一致。用户真实风扇/空调环境和新模型在 iPhone 锁屏下的行为仍需实测。


## 0.4.5 外接麦克风

共享手机采集层启用 AVAudioSession 的 allowBluetoothHFP，并取消固定内置麦克风。24R 录音区域可选自动或某个系统可用输入；自动优先级为 USB 接收器、有线麦克风、蓝牙输入、内置麦克风。手动选择按设备 UID 仅保存在手机本地，也用于同一 App 的短时语音输入。设备不可用时回退到其他可用输入，选择记录保留，重新连接后优先恢复所选设备。

显示名称来自 currentRoute 的实际输入，不以“已经蓝牙配对”或 preferredInput 作为成功收音的证据。空闲时不为刷新列表额外打开音频会话；开始记录后系统会更新可用列表。只有 availableInputs 中的输入可供选择，蓝牙输出设备不会被当成麦克风。

24R 录音中路由变化会在 300 毫秒去抖后按需重建采集格式，保留中断前尾段，重置检测与分段。系统中断等待期间不因设备插拔抢先恢复；手动暂停取消待处理路由任务。普通短时输入在实际设备更换时结束本次会话，避免跨断点继续提交到 Mac 光标。

DJI 官方说明 Mic Mini 支持手机蓝牙直连及接收器的 USB-C/Lightning 连接；实际兼容性与手机/应用有关：[官方支持](https://www.dji.com/support/product/mic-mini)。使用时先在系统蓝牙完成配对，再开始 24R，确认“实际收音”为目标设备。用户当前 iPhone 14 Pro 为 Lightning 接口，接收器方案需匹配该接口的适配器。App 不控制 DJI 的配对、增益、固件或专有 OsmoAudio，也未完成 DJI 硬件联测。

新增输入选择测试覆盖自动选蓝牙、明确选手机、断连回退/重连恢复、接收器优先及空输入列表。iPhone SDK 编译通过；路由与无线音质仍需真实设备验证。

## 0.4.7 Mac 分析工作流与自主 Agent

仅更新 Mac 分析器和任务状态，手机采集、同步协议、数据结构和 Markdown 展示保持兼容，iPhone 无需安装新版本。

Ollama 与云端 OpenAI 兼容模型使用同一套代码编排：日报依次进行 5 次独立调用——活动动线与重要事件、心情与支持、困难与对策、值得肯定的事、汇总与行动计划。前四项各自读取资料，汇总读取原资料及各项结果。前四项返回各自的结构化条目，最后一步返回总览、待办、历史、待确认四组条目；程序控制章节和引用，将专题与总览组装为 Markdown，防止最后一次汇总丢掉某个维度。调用串行执行，Ollama 保持既有 keep_alive 配置。状态通过已有 catalog 接口显示 1/5 至 5/5 的进度。

小时整理继续单次调用，增加保存情绪原话、重要活动、困难和进展线索。日报同时参考小时整理与原始转写；原文较长时按片段等额截取并标注节选，避免只取一天开头。全文大小仍有上限，超限明确报错，不静默丢弃后半天。任一阶段失败或取消不会覆盖已保存日报，自动任务按原重试策略重试完整流程。

Quenda 使用不同执行方式：把完整目标、当日资料、允许的历史范围交给配置的专用 Agent，由它自主决定分析步骤、历史检索和必要的只读工具使用，完成后返回报告；Mac 不向 Agent 强制派发固定的 5 个阶段，也不再预先按固定关键词检索 Quenda 会话。Agent 内部可多轮推理/工具调用。未开启历史关联时明确限定当日资料；需要权限或人工交互时保留原有的会话提示，不自动批准。等待 Agent 的上限为 15 分钟。

情绪仅由文字与事件提供线索，区分用户、他人和视频声音，证据不足不确定归因，不诊断心理疾病。低落时提供具体理解与温和鼓励，困难给可执行的建议，好事给予有依据的认同。动线是记录中可确认的活动/地点变化，不提供 GPS 轨迹；区分计划、回忆、转述和实际发生，收音时间不强行当作事件发生时间。建议不自动成为已承诺待办。

本地 qwen3.5:2b 的首轮自由 Markdown 实测暴露了重复专题、错置时间、缩写引用及把未决定计划放进待办的问题。随后将直接模型流程改为结构化契约：Ollama 与云端都使用相同 JSON 提示及本地解析校验，无需假定都支持 response_format。Ollama 的固定分析阶段使用 think=false 与 temperature=0.3，若模型以 HTTP 400 明确拒绝 thinking 控制则回退到模型默认值；Quenda Agent 不修改推理配置。原生 JSON Schema + 默认长推理在本机 Qwen 3.5 测试中触发 180 秒超时，因此采用兼容的提示/解析契约，不依赖该组合。资料用 S 编号别名供模型引用，由程序还原真实来源 ID；未知编号与无效结构触发该阶段至多一次重试。待办需有可回溯到原始片段的逐字引文，否则移到待确认；未启用或未提供历史时由程序输出明确提示。结构校验并不等于语义事实已被证明，用户仍可点引用核对。参考 [Ollama 结构化输出文档](https://docs.ollama.com/capabilities/structured-outputs)。

最终各专题分别要求活动顺序/重要事件、心情线索/给你的支持、困难/具体对策、进展/具体认同，避免把所有字段都变成事件复述。实际本地 2B 模型仍会过度推断情绪归因，因此报告明确标注情绪与对策为 AI 解读并提供来源核对；待办显示匹配到原始片段的承诺原话，不直接采用模型扩写的动作、沟通渠道或期限。这些工程约束不能保证情绪判断正确，后续专用 Agent 或更强模型仍需真实记录评估。

0.4.7 验收：全量 83 项测试中 79 通过、4 项可选测试跳过。覆盖 Ollama/云端的独立阶段和结果汇总、错误阶段停止且保留旧日报、取消、引用结构校验、承诺引文校验、推理参数不兼容时回退，以及隔离 Gateway 上的单次 Agent 任务和最终答复读取。另行启用当前本地 qwen3.5:2b 的模拟记录实测，最终五阶段流程约 16.5 秒完成；该数字仅对应三条模拟转写，不代表全天数据耗时，实测中的情绪归因局限已如上记录。Mac/iOS SDK 构建通过；新版 Mac 为 0.4.7（build 13），iPhone 保持 0.4.6（build 12），未重新安装手机。重新打开 build/Companion.app 后运行新流程，已有日报可手动更新；没有改动或重启 Quenda Gateway。

## 0.4.8 小时摘要与标签

小时记录作为白天回看与日报索引，不再承担深度分析。Ollama/云端使用一次结构化请求，输出 1–3 条简短事实摘要，以及情绪线索、场景、主题三组可选标签；结构无效时最多重试一次。明确承诺保留为摘要事实，小时记录不生成待办、鼓励、赞赏、对策或心理归因。日报继续原有多阶段流程，并结合原始转写核对。

情绪标签限定为简短线索，要求模型提供可在引用片段中逐字匹配的原话；未通过验证的标签不显示，重复标签合并，每组最多三个。场景和主题也必须带有效来源。模型仍可能漏打标签或误读语义，引用匹配不能保证判断正确。Quenda 小时任务收到同样的轻量目标，由 Agent 自主完成，不使用直接模型的固定 JSON 工作流，也不检索历史。

自动整理复用原文未变化的小时记录，空时段不调用模型。手动“整理一次”重新生成所选日期的小时摘要，可用于更新旧的重分析版本，已有日报不被该操作覆盖。仅更新 Mac，手机沿用已有 Markdown 与引用展示，不变更同步协议或采集。

0.4.8 验收：全量 87 项测试中 82 通过、5 项可选测试跳过，覆盖双 Provider 单次小时调用、排除历史、摘要长度、情绪原话校验、标签去重、手动刷新与日报保留。另行启用本地 qwen3.5:2b 的一条模拟转写测试，最终约 3.1 秒输出两条摘要及情绪、场景、主题标签；此前实测也出现过漏打标签，因此该耗时与输出不代表全天记录质量保证。Mac/iOS SDK 构建通过；Mac 为 0.4.8（build 14），手机仍为 0.4.6（build 12），未重新安装。重新打开 build/Companion.app 生效，旧小时记录可点“整理一次”刷新。

## 0.4.9 Mac 可选择资料库文件夹

Mac 设置新增“Mac 资料库文件夹”：选择父目录（可为已有 Obsidian vault）后，在其中创建 `24R`，也可重新选择已经由本功能创建的资料库根目录。自动写入全部历史记录，后续每次本地记录变化都更新对应日期。更换位置先完成历史写入与位置保存，再切换目标；旧文件保留但不再更新。选择取消不改变配置，非本功能管理的同名非空目录拒绝覆盖。

目录结构：

```text
24R/
  README.md
  Transcripts/YYYY-MM-DD.json
  Transcripts/YYYY-MM-DD.md
  Hourly/YYYY-MM-DD.md
  Reports/YYYY-MM-DD.md
  .24r-vault.json
```

JSON 是只含 transcript/gap 的原始片段数组，使用缩进排版和 ISO 8601 UTC 时间，保留原 ID；文件日期按 Mac 当地日期分组。Markdown 带 date/type/generator/schema_version 属性，引用转换为指向原文或小时/历史日报的 Obsidian 相对链接，原文保留块 ID。日报勾选状态跟随 App 中的状态更新。模型地址、API Key、音频不进入资料库；位置与安全作用域书签保存在 Mac 原记录目录下 `vault-location.json`，不通过手机协议同步。

资料库当前是 App 记录的单向可读副本，原有 Application Support 日文件仍作为恢复来源。Agent 可读取 JSON/Markdown 并在其他文件名或新目录（如 Agent Reports）生成扩展分析；外部改动不会回写 App。校验索引检测生成文件的外部修改，冲突文件不覆盖，并提示先将修改版另存后移走原路径，再点“重新同步资料库”。文件写入使用原子替换；目录丢失或不可写时不阻断已落盘的转写，在 Mac 页面显示同步错误。用户主动重新同步和 App 重启时尝试补齐。同步过程中若失败，已写入的文件保留，新位置尚未切换，修复后可重试。

四项资料库集成测试覆盖历史写入、可解析日期与原文、Markdown 引用、待办状态、重启书签恢复、更换位置保留旧文件、目标冲突、外部编辑保护及原记录继续保存、目录缺失、符号链接不会将生成文件写到资料库外。测试只使用临时目录，没有替用户选定实际保存位置。

## 0.5.0 单一资料源、待办与离线补传

纠正 0.4.9 的双份主数据设计：选择资料库后，Mac 直接读写该目录，不再更新 Application Support 中的独立日文件。后者只保留为一次迁移的旧备份，模型设置、资料库书签仍在 Application Support，凭据仍在钥匙串。App 的内存缓存按文件版本失效、可随时重建；资料库失联/损坏时明确报错，不回退到旧日文件继续写。未选择资料库时仍使用原默认位置。手机的本地副本用于离线阅读，并接收 Mac 完整快照，删除的报告不会因旧片段 merge 而残留。

约定的可编辑源为 `Transcripts/YYYY-MM-DD.json`、`Hourly/YYYY-MM-DD.md`、`Reports/YYYY-MM-DD.md`、`Tasks/YYYY-MM-DD.md`；Transcripts 的 Markdown 是阅读视图，修改原文应编辑 JSON。App 仅检查这四个目录内匹配日期的相应扩展名，不递归读取其他目录或非日期笔记。Markdown 保留 date/type/generator/schema_version 属性；Agent 可按该约定创建日报和待办。记录 ID、时间、引用保存在无正文副本的元数据注释中，小时摘要需保留每小时的注释。

Tasks 是待办唯一来源，使用标准 Markdown 复选框。日报链接到 Tasks；App 将其投影到日报的待办区。外部新增/改写/删除/勾选任务和 App 勾选均直接反映到该文件。生成新日报时保留用户已有任务及完成状态。外部编辑在 Mac 页面约五秒刷新时读取，手机连接时刷新对应日期；报告或小时摘要在模型生成期间被改动时，停止覆盖并保留文件的新版本。

旧 v1 资料库首次打开转为 v2：外部现有日报优先于旧内部正文，原小时 Markdown 保留在 MigrationBackup 后加入可解析标识。新建目录复制当前记录；选择另一已有资料库则直接打开，不把两个资料库合并。其他文件及旧位置保留。没有新的隐藏报告镜像。

离线问题回归命令：`conda run -n kora swift test --filter DayRecordTests.testOfflineDayOldSegmentThroughRelayIsAcceptedAndReplayIsIdempotent`。修复前一天前片段经真实 relay 被 Mac 的一小时时间窗拒收，返回协议错误；修复后保留采集时间成功转写，重复 ID 不重复保存。手机旧代码同时存在无连接时清空分段、连接变化清空内存队列、发送前取出且失败不恢复的问题。现在不再因断连重置分段；每个完成的语音片段先用二进制 plist 落到 PendingAudio，按采集时间 FIFO 补传。Mac 返回匹配的 completedSegmentID 且手机文字保存成功后才删除该文件，空转写也需明确确认。失败保留，连接可用时自动重试（失败后约 30 秒），可手动重试；暂停采集不等待整队补传。旧关键词补传不触发当前的长期保留动作。

缓存仍是 16 kHz 单声道 16-bit PCM，32000 字节/秒，二进制文件无 base64 膨胀。累计片段 1 小时约 115.2 MB，2 小时约 230.4 MB，4 小时约 460.8 MB，24 小时约 2.7648 GB / 2.575 GiB，另有少量元数据和文件系统开销。静音不单独存储，语音片段带最多约两秒前文及三秒尾部静音。上限 4 GB，设备剩余不足约 128 MB 或写入失败则暂停并显示错误，不删除旧缓存。系统备份排除该临时音频目录，iOS 使用首次解锁后文件保护。长期主动保留的 Clips 独立管理。

已完成片段可跨 App 重启恢复；当前尚未结束、最长一分钟的片段仍在内存，强杀/系统终止可能丢失该尾段，正常暂停和系统音频中断会先尝试落盘。iOS 后台补传依赖进程可运行与网络可用；不承诺系统挂起后即时上传，也未完成全天锁屏/耗电测试。

## 0.5.1 Quenda 切换与 24R 音频会话隔离

进入/离开 Quenda 对话时，ConversationView 会取消自己的语音输入；此前空闲 PhoneVoiceStore 也会无条件关闭整个 App 的 AVAudioSession，误停正在运行的 24R。现在 PhoneMicrophone 通过进程共享的 MicrophoneSessionOwnership 管理占用：只有成功激活的实例可以停用音频会话；其他实例的空闲清理、启动失败清理、旧实例的重复停止均不会影响当前录音。另一功能尝试启动时，在修改音频类别/激活之前拒绝占用；原录音实例可继续执行系统中断后的恢复。

24R 后台记录会保留设备连接，但 App 在后台会断开 Quenda。此前 Quenda 的连接任务只监听设备 revision、应用配置 revision 和导航状态，这三者在回到前台时都可能不变，导致 Quenda 一直未连接。连接任务现在包含前后台状态，返回前台时即使共用设备连接没有变化，也重新连接 Quenda；短暂 inactive 状态不重建连接。

验证：音频占用测试在原有无条件关闭实现下失败；前台恢复测试经隔离 Gateway fixture 和真实 Companion relay，复现保留设备连接时返回 Quenda 不重连，修复后通过。测试也覆盖同一录音恢复、另一录音启动被拒、失败启动释放及旧实例重复停止。Conda kora 全量 102 项测试，96 通过、6 项可选测试跳过。本机实际配置的 Quenda Gateway 为 http://127.0.0.1:8000，启用状态正常，独立只读 QuendaStore 连接检查通过；检查未启动/重启 Gateway、发送对话或改动用户会话。硬件麦克风与 iPhone 页面切换仍需实机验收，自动化生命周期测试不代表已完成实机采集验证。
